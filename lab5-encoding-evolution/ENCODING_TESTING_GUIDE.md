### 🔬 การทดลองที่ 1: ผ่าดูขนาดไบต์จริงของข้อมูล `Martin / 1337` (ตอนที่ 3 – ตอนที่ 7)
* ข้อมูลตัวอย่างเดียวกับในหนังสือ:
  `{"userName": "Martin", "favoriteNumber": 1337, "interests": ["daydreaming", "hacking"]}`
* เปรียบเทียบขนาดจริงทีละไบต์:
  1. **Python `pickle` (ตอนที่ 3):** ผูกติดกับภาษา ไม่ปลอดภัย และขนาดใหญ่
  2. **JSON แบบไม่มีช่องว่าง (`81 ไบต์` — ตอนที่ 4):** เปลืองพื้นที่เก็บชื่อช่อง `userName`, `favoriteNumber`, `interests`
  3. **MessagePack (`66 ไบต์` — ตอนที่ 5):** เข้ารหัสแบบไบนารีแต่ยังต้องเก็บชื่อช่องไว้ในทุกข้อความ
  4. **Thrift BinaryProtocol (`59 ไบต์`) & CompactProtocol (`34 ไบต์` — ตอนที่ 6):** เปลี่ยนชื่อช่องเป็นหมายเลขประจำช่อง (`Field Tag #1, #2, #3`)
  5. **Protocol Buffers (`33 ไบต์` — ตอนที่ 6):** เล็กกว่า JSON เกินครึ่งด้วย `Field Tag` + การบีบอัดตัวเลข `Varint`
  6. **Apache Avro (`32 ไบต์` — ตอนที่ 7):** เล็กที่สุดในทุกแบบ เพราะไม่มีทั้งชื่อช่องและไม่มีทั้งหมายเลขประจำช่อง อาศัยการเทียบ `Writer's Schema` กับ `Reader's Schema`

### 🔄 การทดลองที่ 2: จำลอง Rolling Upgrade (Backward vs Forward Compatibility)
กดปุ่มจำลองสถานการณ์จริง 4 รูปแบบ:
1. **`🟢 1. เพิ่มช่องใหม่ + มีค่าเริ่มต้น (Default)`:** พิสูจน์ว่าทั้งโค้ดเก่าอ่านข้อมูลใหม่ (Forward) และโค้ดใหม่อ่านข้อมูลเก่า (Backward) ทำงานร่วมกันได้ 100%
2. **`🔴 2. เพิ่มช่องใหม่แบบบังคับ (Required)`:** พิสูจน์ว่าทำไม **ความเข้ากันได้ย้อนหลัง (Backward Compatibility) ถึงพังทันที** เมื่อโค้ดใหม่อ่านข้อมูลเก่าที่ไม่มีช่องนี้
3. **`🏷️ 3. เปลี่ยนชื่อช่อง (`userName` -> `fullName`)`:** พิสูจน์ว่าทำไม Protobuf/Thrift ถึงเปลี่ยนชื่อช่องได้ตามสบาย (เพราะดูแค่ `Field Tag #1`) แต่ JSON/Avro ต้องระวัง
4. **`🐦 4. ปัญหาตัวเลขใหญ่ Twitter (JSON / 64-bit)`:** เห็นตัวเลขรหัสทวีต 64-bit เพี้ยนคาตาเมื่อถูกอ่านเป็นตัวเลขใน JavaScript (ตอนที่ 4 หน้า 2) หรือถูกตัดทอนเป็น 32-bit (ตอนที่ 6 หน้า 3)
